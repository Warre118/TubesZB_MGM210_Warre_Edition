Part 1

Flashing the radio is now a button

Before

Your TubesZB Silicon Labs FW Flasher add-on already made this possible without a PC. The steps were:

  • Find a .gbl URL that matches this board's pins.
  • Disable ZHA or Zigbee2MQTT.
  • Enter IP:6638, the firmware URL and the probe method in the add-on options.
  • Start the add-on and read its log.
  • Re-enable ZHA.
Now

The coordinator knows which firmware fits it and tells you when there's a newer build. Open its web page (or the update entity in Home Assistant), pick a firmware type and channel, and press Flash.

The ESP32 downloads, verifies and flashes the EFR32 itself in about half a minute. ZHA stays configured and reconnects on its own, with no URLs, add-on or integration to switch off.

What the user sees

  1. ChooseFirmware type (Zigbee NCP, Thread RCP, Zigbee router) and channel (stable or latest). Or use Choose version to see every build in the repo, with the installed one tagged.
  2. VerifyThe device fetches the signed manifest for that choice. Flash only appears once there's a verified offer that differs from what's on the radio.
  3. ConfirmA checklist: backup made, bridge offline ~30 s, don't unplug. Switching stack type gets its own red checkbox, because the network is lost.
  4. InstallLive download and flash progress on the page, then the result. The new version shows up as installed.

What happens under the hood

Build serverFollows NabuCasa/silabs-firmware-builder and builds the Yellow firmware with TubesZB pins.
→
firmware branchindex.json, plus per type/channel a .gbl, signed manifest.json and release notes.
→
ESP32Checks the ECDSA P-256 signature, downloads into the spare OTA partition, checks sha256 and size.
→
EFR32PA00 low during reset puts it in the Gecko bootloader; the image goes over XMODEM.
  • Nothing reaches the radio unless both checks pass. A manifest without a valid signature, or signed for another type or channel, is refused.
  • The bootloader is never touched. If an upload fails halfway, the radio stays in the bootloader and you press Install again.
  • Switching stacks works both ways. The bootloader is reached through GPIO, whatever firmware is running.
  • It needs a person. The device checks for updates at start-up and once a day, but only installs when someone presses Install.

Manifest settings that differ from the Yellow

The TubesZB uses the same MGM210 module as the Home Assistant Yellow, so the build starts from Nabu Casa's Yellow manifest with these changes:

SettingValueWhy
UARTUSART0, TX PA06, RX PA05, 115200From your schematic; the Yellow has TX/RX swapped
Flow controlnoneNo RTS/CTS between ESP32 and EFR32. The Simplicity SDK dropped ncp-uart-sw, so it's the hardware UART component with flow control off.
LED / PTIoffNo LED on PB01; PC04/PC05 not needed
Tablesas on the YellowSame RAM

Your existing Gecko bootloader accepts these images as-is, and going back to your 7.4.3 firmware is always possible.

Part 2

A web page that tells you what's going on

The page is ESPHome's web_server v3 plus a small layout script (tubeszb-webui.js, served as /0.js). Groups sit in pairs of equal height, centred, and collapse to one column on a phone. Everything is visible; there's no Show All button.

Illustration of the layout with example values. The real page uses ESPHome's own styling.

Status at a glance

One row says whether Home Assistant and the Zigbee client (ZHA / Z2M) are connected. CPU is measured over 10 s from FreeRTOS run-time stats on both cores.

Radio controls

Restart the EFR32 or put it in bootloader mode from the page, without touching the board.

Debug log

Newest line on top, at INFO level: connects, disconnects, OTA, warnings and errors.

Optional login

First start shows a Create a login dialog. HTTP Digest auth, credentials stored in NVS, not in the YAML. A reset button in Home Assistant covers a forgotten password.

The same entities show up in Home Assistant, including the radio update entity with release notes, so the device can be managed from there too.

Caveats

Where it stands

  • Tested on one MGM210 2022 (ZHA, ~55 devices). The coordinator and Thread builds are the ones I've run; the Zigbee router build compiles but hasn't run on a TubesZB yet.
  • Needs ESPHome 2026.10 or newer for uart_tcp. Entity names changed from your config, so HA creates new entity IDs.
  • The web page loads ESPHome's web app from oi.esphome.io, so the browser needs internet access.
  • HTTPS certificate checking is off on the ESP32 (no CA bundle in the Arduino build). Integrity rests on the signed manifest and sha256 instead.
